# MedVista

**AI-powered clinical imaging & patient intelligence platform.**

MedVista is a unified clinical workspace where physicians can manage patients, ingest and review DICOM imaging, run AI-assisted analysis, compare studies over time, and draft reports — all backed by real, persisted data. It is a research/education/prototype system, not an autonomous diagnostic tool.

> **Status:** Phase 1 (Foundation) complete and tested. See [Roadmap](#roadmap) below.

---

## The one rule that shapes everything here

**Nothing is hardcoded.** No fake patients, counters, findings, or dashboard numbers. Every number and label in the UI comes from a real database query, a real AI model, or an explicit empty state ("No imaging studies available" — not a placeholder number). If a feature isn't built yet, its UI says so plainly instead of pretending to work. This constraint is enforced from the schema up, not bolted on in the frontend.

AI output is always labeled as decision support — *AI finding*, *flagged region*, *requires physician review* — never as a diagnosis. The physician is always the final clinical authority.

## Architecture

```
Frontend (Next.js/TS)
   │  cookie session (httpOnly) → BFF proxy → Bearer token
   ▼
FastAPI backend  ──▶  PostgreSQL (schema below)
   │                        │
   ├─▶ Redis (jobs/cache, Phase 4+)     
   ├─▶ Orthanc / DICOMweb (Phase 2+)
   └─▶ AI orchestration (Phase 4+) — imaging models + clinical LLM,
       both behind a swappable provider interface; report themselves
       "unavailable" rather than fabricate output when unconfigured.
```

Every entity in the [full schema](#database) exists in the database from day one, even for features not yet built — so later phases add endpoints and UI against real tables instead of retrofitting the data model.

## Database

19 tables, fully normalized — no JSON-blob shortcuts. Core groups:

- **Identity & access:** `organizations`, `users` (role enum: super_admin, hospital_admin, doctor, radiologist, technician, researcher)
- **Patient record:** `patients`, `clinical_history`, `laboratory_results`, `medications`, `patient_events`
- **Imaging:** `studies`, `series`, `imaging_instances`
- **AI:** `ai_models` (registry), `ai_analyses` (jobs), `ai_findings` (results, with confidence/measurement/evidence/status)
- **Review artifacts:** `annotations`, `measurements`, `reports`, `report_versions`
- **Operational:** `audit_logs`, `notifications`

Tables for not-yet-built phases (imaging, AI, reports, labs, ...) exist and are queried for real — they simply return empty results until those phases populate them. This is why dashboard counts, timelines, and organ status can be computed with real `COUNT`/`JOIN` queries from day one instead of being stubbed with fake numbers.

## Security & RBAC

- JWT bearer auth (backend), httpOnly session cookie via a Next.js BFF route (frontend) — no token ever touches frontend JS.
- Every clinical endpoint enforces role checks **server-side** (`require_roles(...)` dependency) — frontend button visibility is never the security boundary.
- Every patient/study query is scoped by `organization_id`; cross-organization access returns `404`, not `403`, to avoid confirming a record's existence.
- Every mutating and every patient-viewing action writes an `audit_logs` row (actor, action, resource, timestamp).
- Passwords hashed with bcrypt; secrets only ever read from environment variables (see `.env.example`).

## Getting started

```bash
cp .env.example .env        # fill in secrets for local dev
docker compose up -d postgres redis orthanc
cd backend
python -m venv .venv && .venv/Scripts/activate  # or source .venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
python -m scripts.seed       # optional — synthetic demo data only
uvicorn app.main:app --reload
```

```bash
cd frontend
npm install
npm run dev
```

Backend tests (run against a real Postgres, not mocks):

```bash
cd backend
DATABASE_URL=postgresql+psycopg://medvista:medvista@localhost:5432/medvista pytest -q
```
